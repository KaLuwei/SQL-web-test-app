專案模擬案例

全通路 3C 電商營運與顧客行為分析資料庫

本系統模擬一家中大型 3C 數位電商與實體門市整合的營運資料庫。提供營運團隊、行銷人員與數據分析師即時查詢訂單狀況、會員消費貢獻度及庫存告警。

1. 使用對象 (Target Users)

  • 數據分析師： 撰寫複雜報表，挖掘潛在高價值 VIP 客戶。
  • 行銷營運團隊： 評估促銷活動銷售量，篩選符合忠誠度條件之會員。
  • 庫存倉管主管： 監控庫存水平，預防熱銷產品缺貨。

2. 核心解決問題

  • 過往跨部門無法即時串聯「會員等級」與「實際購買品項」。
  • 需要多表關聯（JOIN）才能精準算出一筆訂單的實收金額與商品明細。
  • 處理退貨/取消訂單對營收統計的干擾問題。

3. SQL 應用預期效益

  • 透過多表關聯 (JOIN) 匯整顧客購物全貌。
  • 利用分組聚合 (GROUP BY / HAVING) 自動篩選大客戶。
  • 實作欄位條件過濾 (WHERE / CASE) 計算淨銷售額。

深入觀念解析

SQL 語法微調對查詢結果之影響對比

實務上常常因為一個關鍵字（如 JOIN 類別、WHERE 位置或計數函數選擇）而導致資料遺漏或計算錯誤。以下為常見差異對照：

案例 1：INNER JOIN (交集) vs LEFT JOIN (左外連結)

商業目標：檢視會員消費狀況與喚醒潛在顧客
寫法 A：使用 INNER JOIN 
SELECT users.user_id, users.username, orders.order_id 
FROM users 
INNER JOIN orders ON users.user_id = orders.user_id;
結果特徵： 僅回傳「至少成立過一次訂單」的會員。未曾消費的會員（如 user_id=5, 6）會被過濾。
寫法 B：使用 LEFT JOIN 
SELECT users.user_id, users.username, orders.order_id 
FROM users 
LEFT JOIN orders ON users.user_id = orders.user_id;
結果特徵： 保留左表 (users) 所有會員。未下單者相對應的 order_id 欄位會顯示為 NULL。

案例 2：WHERE (分組前過濾) vs HAVING (分組後聚合過濾)

商業目標：計算已完成訂單的 VIP 大客戶
正確觀念：WHERE 排除無效單 + HAVING 篩選總額 
SELECT user_id, SUM(total_amount) AS total_spent
FROM orders
WHERE status = 'Completed'  -- 1. 先剔除取消/待處理單
GROUP BY user_id
HAVING total_spent > 3000;  -- 2. 再針對計算出的總額過濾
常見錯誤：試圖在 WHERE 中放置聚合函數 
-- ❌ 錯誤語法示例
SELECT user_id, SUM(total_amount)
FROM orders
WHERE SUM(total_amount) > 3000 -- 錯誤！SQL 語法規則不允許
GROUP BY user_id;

案例 3：COUNT(*) 列數計算 vs COUNT(column) 排除 NULL 計算

商業目標：正確統計會員的實際下單次數
寫法 A：COUNT(orders.order_id) 
SELECT u.user_id, u.username, 
       COUNT(o.order_id) AS actual_order_count
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
GROUP BY u.user_id;
寫法 B：COUNT(*) 誤計算 NULL 列 
SELECT u.user_id, u.username, 
       COUNT(*) AS row_count
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
GROUP BY u.user_id;
